# Отчёт по ДЗ: оптимизация inference pipeline для `sergeyzh/rubert-mini-frida`

## Цель работы

Целью работы было сравнить три варианта инференса модели эмбеддингов `sergeyzh/rubert-mini-frida` на CPU:

1. базовый inference через `transformers`;
2. inference через `ONNX Runtime`;
3. inference через `ONNX Runtime` с динамическим батчированием.

Задача состояла в том, чтобы оценить, как оптимизация модели и оптимизация сервинга влияют на задержки, пропускную способность и потребление ресурсов.

---

## 1. Модель и постановка эксперимента

В работе использовалась модель `sergeyzh/rubert-mini-frida` с Hugging Face. В карточке модели указано, что для получения sentence embeddings рекомендуется использовать **mean pooling**, а рекомендуемый размер контекста не превышает **512 токенов**. Также модель ориентирована на работу с префиксами; в данной работе использовался префикс `categorize: `.

Все эксперименты проводились на CPU. Для честного сравнения во всех трёх частях использовались одинаковые входные данные, одинаковый `max_length=512` и одинаковая постобработка эмбеддингов.

---

## 2. Выбранные метрики

Для сравнения были выбраны следующие метрики:

* **Latency p50/p95/p99** — показывают типичную и хвостовую задержку ответа.
* **Throughput (req/s)** — показывает, сколько запросов сервис способен обработать за секунду.
* **Peak RSS memory (MB)** — показывает пиковое потребление памяти процессом.
* **CPU time / CPU utilization** — показывает вычислительную нагрузку на процесс.

Выбор этих метрик объясняется тем, что для inference-сервиса важно не только быстро отвечать на одиночный запрос, но и устойчиво выдерживать поток запросов при разумной цене по ресурсам.

---

## 3. Часть 1 — базовый inference через `transformers`

### Реализация

В первой части был реализован HTTP-сервис на FastAPI. Модель загружалась через `transformers`, после чего для выхода `last_hidden_state` применялся `mean pooling`, а затем L2-нормализация эмбеддингов.

### Результаты бенчмарка

| Metric            |  Value |
| ----------------- | -----: |
| p50 latency, ms   | 368.08 |
| p95 latency, ms   | 436.26 |
| p99 latency, ms   | 455.54 |
| throughput, req/s |  43.32 |
| peak RSS, MB      | 778.29 |
| CPU time, sec     |  35.16 |

### Вывод

Базовый вариант является самым простым с точки зрения реализации и хорошо подходит как отправная точка для сравнения. Его главный плюс — прозрачность и минимальное количество дополнительных компонентов. Главный минус — более высокая задержка и меньшая пропускная способность по сравнению с оптимизированными вариантами.

---

## 4. Часть 2 — inference через ONNX Runtime

### Реализация

Во второй части модель была экспортирована в ONNX. Для экспорта использовался Optimum, который поддерживает экспорт моделей Hugging Face в формат ONNX, пригодный для выполнения через ONNX Runtime.

После экспорта был реализован отдельный FastAPI-сервис. Внутри сервиса модель исполнялась через `onnxruntime.InferenceSession`, а pooling и нормализация выполнялись уже в Python/Numpy.

### Результаты бенчмарка

| Metric            | Baseline |   ONNX |
| ----------------- | -------: | -----: |
| p50 latency, ms   |   368.08 | 178.69 |
| p95 latency, ms   |   436.26 | 451.05 |
| p99 latency, ms   |   455.54 | 610.45 |
| throughput, req/s |    43.32 |  72.34 |
| peak RSS, MB      |   778.29 | 862.12 |
| CPU time, sec     |    35.16 |  12.92 |

### Анализ

Переход с baseline inference на `onnxruntime` дал заметный выигрыш по типичной задержке и пропускной способности на CPU. По результатам бенчмарка throughput вырос с 43.32 req/s до 72.34 req/s, а p50 latency снизилась с 368.08 ms до 178.69 ms. Также уменьшилось суммарное CPU time: с 35.16 sec до 12.92 sec.

При этом ONNX-вариант показал более высокое потребление памяти (862.12 MB против 778.29 MB у baseline), а хвостовые задержки p95/p99 не улучшились: p95 выросла до 451.05 ms, p99 — до 610.45 ms.

Итог: ONNX заметно ускорил инференс на CPU в среднем случае и повысил throughput, но не решил проблему хвостовых задержек.

---

## 5. Часть 3 — dynamic batching

### Идея

В третьей части был реализован dynamic batching: входящие HTTP-запросы сначала складываются в очередь, после чего worker в течение короткого окна времени собирает несколько запросов в общий batch и отправляет их на один проход модели.

### Реализация

В работе использовалась очередь + отдельный worker-поток. Параметры batching:

* `max_batch_size = 32`
* `batch_timeout_ms = 8`

### Результаты бенчмарка

| Metric            |   ONNX | ONNX + dynamic batching |
| ----------------- | -----: | ----------------------: |
| p50 latency, ms   | 178.69 |                  237.49 |
| p95 latency, ms   | 451.05 |                  351.00 |
| p99 latency, ms   | 610.45 |                  467.59 |
| throughput, req/s |  72.34 |                   63.25 |
| peak RSS, MB      | 862.12 |                  869.05 |
| CPU time, sec     |  12.92 |                   15.11 |

### Анализ

Dynamic batching был реализован поверх ONNX inference через очередь запросов и worker. В настройках использовались `max_batch_size=32` и `batch_timeout_ms=8`.

По результатам бенчмарка dynamic batching не дал прироста throughput относительно обычного ONNX inference: throughput составил 63.25 req/s против 72.34 req/s у ONNX без batching. Также p50 latency выросла с 178.69 ms до 237.49 ms, что ожидаемо, так как запросы некоторое время ожидают формирования батча.

Однако batching улучшил хвостовые задержки: p95 уменьшилась с 451.05 ms до 351.00 ms, а p99 — с 610.45 ms до 467.59 ms. Потребление памяти немного выросло: 869.05 MB против 862.12 MB.

Итог: в данном сценарии нагрузки dynamic batching не улучшил среднюю скорость и throughput, но сделал распределение задержек стабильнее и снизил хвосты p95/p99.

Следует учитывать, что эффект dynamic batching зависит от характера нагрузки: числа одновременных запросов, длины текстов, размера окна ожидания и максимального размера батча. В данном эксперименте использовались короткие запросы (`texts_per_request=1`) и умеренная конкуренция (`concurrency=16`), поэтому batching не смог полностью раскрыть потенциал по throughput.

---

## 6. Общий вывод

В работе были сравнены три варианта inference pipeline для модели `rubert-mini-frida` на CPU: baseline через `transformers`, inference через `onnxruntime` и ONNX inference с dynamic batching.

Лучший результат по throughput показал ONNX-вариант без batching — 72.34 req/s. Он же дал наименьшую p50 latency — 178.69 ms. Dynamic batching в данном эксперименте не оказался самым быстрым вариантом, но позволил уменьшить хвостовые задержки p95/p99 по сравнению с обычным ONNX inference.

Таким образом, оптимизация через ONNX оказалась наиболее эффективной для ускорения типового инференса на CPU, а dynamic batching полезен прежде всего как способ стабилизировать задержки под конкурентной нагрузкой.
